## Elegir modo

Interpreta `$ARGUMENTS` antes de ejecutar nada:

- `setup`: lee [setup.md](setup.md) y sigue la configuración asistida. No lances implementador/QA/documentalista ni prepares una funcionalidad en este modo.
- `ready <ruta-spec>`: lee la spec y muestra su alcance y decisiones pendientes. Ejecuta `python3 harness/harness.py spec-review <ruta-spec> --session-id "${CLAUDE_SESSION_ID}"`, citando la ruta. Usa el campo `spec` devuelto: la revisión coloca el documento en `Draft`. Muestra literalmente `reply` y espera la confirmación del usuario. El hook registra `LISTA PARA IMPLEMENTAR <código>`; después ejecuta `spec-accept <ruta-spec-devuelta> --session-id "${CLAUDE_SESSION_ID}"`. Solo ese comando puede marcarla lista y moverla a `Ready`. Esta confirmación no inicia un trabajo ni aprueba una entrega; informa el estado y la nueva ruta y termina. Si `reply` es null, ya está autorizada y tampoco se inicia automáticamente. No invoques el hook, no escribas recibos ni deduzcas consentimiento de haber completado la redacción.
- `recover <job-id>`: recuperación explícita de una conversación. El usuario debe cerrar la sesión anterior y sus agentes. Ejecuta `recover <id> --session-id "${CLAUDE_SESSION_ID}"`, muestra literalmente su `reply` y termina el turno. Tras el mensaje exacto `RECUPERAR <id> <código>`, ejecuta `accept-recovery <id> --session-id "${CLAUDE_SESSION_ID}"`. El hook registra esa autorización; no lo invoques ni escribas consentimientos. La recuperación no aprueba el producto. Usa brief y, si está en revisión humana, emite otra revisión validada. Si no se acredita el cierre anterior, conserva el bloqueo; no reasocies por carpeta o token.
- Una ruta de spec: desde la raíz del controlador, ejecuta `python3 harness/harness.py start <ruta> --session-id "${CLAUDE_SESSION_ID}"`, citando la ruta. Una spec por sesión: no uses `--launch`, `claude --bg`, `attach` ni otra sesión coordinadora. El controlador prepara worktrees/clon/Graphify y devuelve `brief`; continúa aquí con ese ID y este controlador. Si se repite la orden, recupera el mismo trabajo, sin duplicarlo. Para otra spec el usuario abre otra sesión. Si falta setup, sigue setup.md y retoma la orden original. El instalador debe haber registrado el hook local UserPromptSubmit: después de actualizar, abrir una sesión nueva carga las instrucciones, permisos y hook. No prepares recursos si el hook está deshabilitado o falta: informa la instalación pendiente.
- Varias rutas: explica que se admite una spec por conversación; no prepares trabajos ni elijas una sin que el usuario lo indique.
- `<job-id> <ruta-controlador>`: modo interno de trabajo preparado, descrito abajo. La ruta del controlador puede contener espacios: trata todo lo que sigue al ID como la ruta absoluta. Reanuda solo en la sesión asociada al trabajo; los trabajos antiguos lanzados por el controlador conservan su modo de sesión gestionada.

- Sin argumentos: explica brevemente `/harness setup`, `/harness ready specs/Draft/mi-feature.md` y `/harness specs/Ready/mi-feature.md`, sin iniciar recursos.

Redacción de specs: usa `specs/plantilla-spec.md`, guarda en `specs/Draft/<nombre>.md` y conserva `Estado: borrador` por defecto. Si hay recursos propios, usa `specs/Draft/<nombre>/spec.md`: se mueve la carpeta completa. Completar requisitos, resolver dudas o aprobar una maqueta no autoriza implementar. Antes de editar una spec autorizada que aún no tiene trabajo, ejecuta `spec-draft <ruta-spec>` y usa la nueva ruta en Draft; después solicita autorización para la nueva versión. `spec-status <ruta-spec>` consulta la autorización efectiva. Cualquier edición de contenido invalida el recibo anterior, incluso si el texto aún dice lista o está en Ready. La autorización puede darse en una sesión de redacción y usarse en otra sesión de implementación del mismo proyecto. Una spec que ya tiene trabajo continúa por el flujo de ese trabajo: no uses estos comandos para cambiar su autorización o reiniciarla.

Organización de specs existentes: `python3 harness/harness.py spec-organize` muestra el plan; `--apply` lo aplica con respaldo y sin trabajos abiertos. Úsalo cuando se solicite organizar el proyecto. Conserva recibos válidos y enlaces, y deja en Draft las specs sin autorización vigente. Nunca infieras permiso de la carpeta ni muevas archivos a mano para eludir la revisión. Las rutas anteriores se resuelven únicamente si identifican una spec sin ambigüedad.

Si `start` rechaza una spec en borrador o sin autorización vigente, informa el bloqueo y ofrece el modo `ready`; no cambies su estado ni prepares recursos para sortearlo.

Si el lanzamiento falla o informa que falta el prompt inicial, entrega el bloqueo y la recuperación indicados por el controlador; no anuncies que el agente está trabajando ni repitas `start`.

Si existe `.harness-parent.json` estás dentro de un trabajo: conserva ese trabajo y usa su controlador original; no configures ni prepares otra spec desde aquí. Una orden setup en un trabajo activo debe dirigir al usuario a su sesión de origen.

## Trabajo preparado

Conduce únicamente el trabajo que acaba de devolver start o el indicado por ID y ruta de controlador en modo recuperación. Comprueba que `brief.conversation.sessionId`, si existe, coincide con `${CLAUDE_SESSION_ID}`; si difiere, ofrece reanudar la conversación original o el modo explícito `/harness recover <id>`; no continúes con una identidad distinta. No prepares otro trabajo ni invoques otros agentes coordinadores. Puedes operar únicamente en los worktrees declarados para este ID; para conflictos remotos, también en los árboles temporales que declare `brief.synchronization.conflicts`. El código de control no se modifica durante una funcionalidad.

1. Ejecuta `python3 <controlador>/harness/harness.py brief <id>` para obtener rutas, versiones, suites, resúmenes y referencias; lee las specs y el reporte QA anterior si existe. No cargues state.json completo; usa `show <id>` solo para diagnóstico y abre secciones concretas de configuración si faltan datos. En modo conversacional conserva el directorio de la sesión en la raíz del controlador. Pasa rutas absolutas a cada subagente y exige `git -C <worktree>`/cwd explícito en todos sus comandos: no edites producto en el checkout original. No uses EnterWorktree ni crees worktrees adicionales. Espera a cada subagente antes de pasar de etapa; todos deben haber terminado antes de finish. Lee `worktrees` y pasa el mapa completo a cada agente; si no existe, es un trabajo de un repositorio. Lee AGENTS.md, CLAUDE.md y CLAUDE.MD existentes en cada árbol. Solo trabaja en estos árboles; no copies ni uses `.env` de otro entorno. No hagas commits, pushes ni PRs directamente: únicamente el controlador puede publicarlos mediante `finish`, después de aprobación humana y documentación. No hagas merges o despliegues. No uses codebase-memory-mcp ni sus hooks.
2. En `implementing`, invoca **harness-implementer**, espera su resultado y no hagas cambios de producto por tu cuenta. Pasa spec, mapa de worktrees, bases por repositorio, controlador e ID, y hallazgos anteriores de brief/qa.json si existen. Durante implementación usa pruebas dirigidas, incluso si todavía no existe un recibo; reserva la suite completa y el build general al controlador. Después ejecuta `verify <id>`. Los logs están en `attempts/<n>/` y `show` muestra grupos ejecutados/reutilizados, razones y tiempos. Lee solo el resumen y logs de fallos. `verify` y `recheck` reutilizan grupos vigentes; `verify --force` obliga a ejecutarlos de nuevo y se reserva para investigar una invalidación dudosa. Si falla por código/tests y queda en `blocked`, entrega el error al implementador y repite `verify`; no llames además a `feedback`, pues el fallo ya consumió un intento. Si es `blockedPhase=upstream`, sigue la sincronización descrita abajo. Para otra infraestructura/migración o `paused`, detente. No ocultes fallos preexistentes ni declares integración/E2E aprobada por un build exitoso.
3. En `ready_for_qa`, ejecuta `qa-start <id>`, luego `qa-template <id>` y `brief <id>`. Pasa al **harness-qa** ese resumen y la ruta del reporte generado; la versión vigente viene de este qa-start. Si hay hallazgos abiertos, prima `fail` aunque QA haya añadido tests: valida/registra el reporte de la qaVersion revisada y devuelve todos los hallazgos al implementador; verifica una sola vez después de corregirlos junto con los tests nuevos. `qa-result` admite cambios posteriores a la revisión solo para resultados negativos, nunca para aprobar. Si devuelve `tests_added` sin hallazgos abiertos, ejecuta un solo `recheck` para el lote y repite qa-start/template/brief antes de reanudar QA con su traspaso y el delta. No solicites un informe firmado sobre la versión anterior ni lo corrijas tú. Antes de `qa-result <id> <ruta>`, ejecuta `qa-check <id> <ruta>`: sus errores son de formato/evidencia, no requieren repetir suites. QA debe resolverlos sin ocultar hallazgos. Solo registra el reporte cuando la validación pase.
4. QA debe completar exploración con Playwright MCP en Chrome visible y E2E repetibles con Playwright CLI/tests en headless, sin ventanas ni modo UI/debug, cerrar Chrome y devolver un reporte JSON con evidencias separadas para ambas tareas. Ejecuta `qa-result <id> <reporte>`. Si falla, devuelve los IDs al implementador y repite desde el paso 2; respeta el límite del controlador. Ante fallos de infraestructura o migraciones, detente con el bloqueo concreto. No repares a mano un clon: el usuario dispone de `reset-db` para repetir desde el snapshot.
5. En `awaiting_human_approval`, entrega localhost del frontend, rama/worktrees, versión conjunta, cuenta de prueba, clon y resumen QA. En modo conversacional ejecuta `review <id> --session-id "${CLAUDE_SESSION_ID}"` y muestra literalmente su `reply` (por ejemplo `APROBAR a1b2c3d4`), explicando que autoriza documentación, PR, espera de CI y de tu merge, y limpieza posterior, sin fusionar automáticamente. **Termina el turno y espera a que el usuario escriba esa frase en el chat.** No uses AskUserQuestion para esta confirmación: el hook UserPromptSubmit recibe mensajes directos. Tras recibirla, ejecuta `accept-review <id>`; solo continúa cuando el controlador devuelva `documenting`. Nunca invoques conversation.py, fabriques eventos, escribas consentimientos ni ejecutes approve: el hook registra la respuesta real y accept-review valida su versión y evidencia. Un “ok”, permiso de herramienta o respuesta a una duda no aprueba. Si el hook no registró consentimiento, informa el problema; no lo suplantes. Para trabajos antiguos sin `conversation`, conserva la aprobación manual por terminal `approve <id> --version <approvedCandidate>`.
6. Si el usuario pide correcciones, ejecuta `feedback <id> "resumen"` y vuelve al implementador. Si editó archivos, exige `recheck <id>` antes de un nuevo visto bueno. No cierres el preview ni restaures el clon durante su revisión.
7. Solo en `documenting`, invoca **harness-documenter** para actualizar los docs afectados de ambos árboles. Entrega el resumen de `brief`, decisiones aprobadas, diff y archivos/secciones de docs afectados; no el state.json completo ni todo el historial. Después ejecuta `finish <id>`. Si cambia producto o hay enlaces inválidos, no completes. En trabajos nuevos con publicación habilitada, `finish` publica los PR y entrega el cierre a Python: termina tu turno y no edites, pruebes ni consultes CI en bucle. El proceso espera CI sin modelo y pasa a `awaiting_merge`; mantiene previews, clon y worktrees hasta que el usuario fusione todos los PR. Detecta las fusiones automáticamente, revalida CI y después detiene previews y clon, y elimina worktrees y ramas locales; conserva esta conversación de usuario (solo detiene sesiones gestionadas del modo antiguo); conserva PR, ramas remotas y evidencias. Si `finish` queda en `blockedPhase=publishing`, corrige únicamente el índice/documentación admitida y repite `finish`; valida aprobación, producto y evidencias sin repetir QA por un arreglo administrativo. Conserva los commits/PR ya creados. Para bloqueos posteriores de CI/merge/limpieza usa `finalize <id>`. No hagas reset del índice ni borres archivos desconocidos para desbloquear. En trabajos antiguos sin publicación registrada, conserva el entorno como antes.

Sincronización entre specs: `start` toma la base remota actual y `verify` integra avances antes de las comprobaciones. QA, revisión, aprobación y publicación detectan cambios posteriores. Ante `blockedPhase=upstream`, ejecuta `sync <id>` una vez; no uses feedback, no repitas implementación completa ni cambies estados. Si declara conflictos, invoca al implementador únicamente para resolver y hacer `git add` de los archivos indicados en los árboles temporales de `brief.synchronization.conflicts`; conserva el worktree de producto y repite `sync` después. Solo el controlador hace el merge/commit. Si necesita una decisión de negocio, pregunta. Una dependencia explícita entre entregas se registra con `sync <id> --after <otro-id>`; no la infieras solo por nombres de archivos. Si falta una fusión de un trabajo que abarca dos repositorios, conserva la espera sin consultar en bucle: continúa cuando se complete.

Si `sync` devuelve `current`, continúa en la etapa actual. Si devuelve `integrated`, sigue `synchronization.lastResult.next`: `verify` reutiliza grupos cuyas entradas/evidencias siguen vigentes y después pasa QA sobre el delta; cambios de producto requieren nueva revisión humana. `review` solicita la frase vigente sin repetir QA equivalente; `finish` conserva una aprobación acreditada cuando solo cambió documentación. No vuelvas a lanzar al documentalista si ya terminó y los docs siguen correctos. Ninguna integración remota consume ciclos de corrección; el límite predeterminado es **15 ciclos totales**, no quince adicionales. Si el cierre de Python detecta una base nueva mientras espera CI/merge, se bloquea conservando recursos y PR: al retomar esta conversación sigue este mismo procedimiento, sin force push ni otro PR. No hay una cola global de aprobaciones: dos specs avanzan a la vez. No se fusiona main automáticamente.

Preguntas: consulta primero specs y decisiones ya recibidas. Para una decisión indispensable utiliza `AskUserQuestion` en la sesión principal, con opciones/texto libre. Si un subagente devuelve `needs_input`, transmite su pregunta fielmente y reanúdalo con la respuesta. No lo reemplaces por una suposición ni gastes llamadas esperando. Las conversaciones y solicitudes las conserva Claude Code; consulta `claude agents` para otras sesiones. Si una sesión debe reiniciarse, recupera primero el estado del controlador y su conversación original.

Los subagentes reciben solo contexto pertinente, no todo el historial. Pasa rutas de spec/reporte, checkPlan/testReports, feedback y qaContext con el delta del ciclo; no pegues informes enteros ni logs verdes. Cada traspaso resume criterio/hallazgo, archivos, pruebas dirigidas y pendiente (orientativamente hasta 250 palabras; detalles en los archivos ya existentes). Cada nuevo ciclo de corrección inicia implementador y QA nuevos: no reanudes el historial del ciclo anterior. Reanuda dentro del mismo ciclo solo para responder una pregunta o continuar tras un único lote `tests_added`; si hubo compactación, usa también uno nuevo. Entrega `qaContext`, el último reporte y el traspaso breve, sin reconstruir toda la sesión. No crees documentos por ciclo: usa la salida del agente y los artefactos existentes. Usa el modelo de la sesión principal: los agentes declaran `model: inherit`; al invocarlos o reanudarlos omite el parámetro `model` para no anular esa herencia. Conserva el esfuerzo Extra (`xhigh`). Tras un límite de uso, retoma desde brief y artefactos guardados; no repitas trabajo terminado. Si el límite de correcciones queda agotado, informa el estado `paused`; nunca amplíes el límite tú mismo.

Al retomar `blocked`, identifica su causa en eventos/logs y no repitas automáticamente una operación de efectos inciertos. En `qa`, reanuda la revisión de la versión registrada. En `checking`, consulta una vez `show.execution`: si dice `interrupted`, ejecuta `verify` una vez; reconcilia bajo bloqueo, conserva recibos y no consume un ciclo por interrupción. Si dice `running`, hay un comando propio vivo: espera su resultado, sin lanzar otro ni consultar en bucle. `unknown` y `preparing` interrumpido requieren diagnóstico; no edites estados. Una interrupción en migración conserva el bloqueo hasta revisar el clon. Si el clon está detenido tras un reinicio, `verify` recupera automáticamente el clon existente con identidad, volumen y puerto fijos y reutiliza recibos vigentes; después requiere QA fresco. `resume-runtime <id>` queda como recuperación explícita. Ninguno restaura datos ni conserva aprobación de evidencia viva. Si Docker está apagado o el clon falta, informa el bloqueo sin bucles de reintento. Un clon antiguo con puerto dinámico requiere decisión explícita. Nunca interpretes un estado desconocido como aprobación.

En `publishing`, `awaiting_ci`, `awaiting_merge` o `cleaning`, el cierre ya pertenece al controlador: informa el estado y termina, sin delegar otros agentes. Para fallos de publicación/CI no ejecutes `verify`, `recheck` ni `feedback` automáticamente; primero resuelve el impedimento. `show <id>` muestra PR, CI y avance de limpieza.

Permisos: una denegación explícita se comunica con operación y motivo; no reformules comandos para eludirla ni desactives el clasificador. Un timeout transitorio admite como máximo un reintento equivalente si el sistema lo permite. Continúa solo trabajo independiente autorizado. La configuración solicita modo manual, pero no garantiza la política efectiva de subagentes.

Para medir, usa `metrics <id>` al final o bajo petición; `--transcript <ruta-jsonl-de-la-sesión>` agrega tokens locales sin modelo. No consultes métricas en bucle. Solo todos los PR fusionados y verificados permiten finalizar; cerrado sin fusionar sigue bloqueando. No anuncies recursos eliminados hasta que `show` indique completed.

Capacidad: los comandos pesados del controlador comparten una reserva local (uno por defecto); dos specs siguen permitidas. `show.execution.resourceWait` explica la espera y esta no consume ciclo. No lances suites paralelas fuera del controlador para esquivar la reserva. Si se agota la espera, informa el bloqueo; no atribuyas un 137 a OOM sin evidencia del sistema.

Chrome y recuperación: `qa-start` habilita QA sin reservar el navegador. Entrega `brief.browser`, `qaContext.testDelta` y `qaCheckpoint` al agente. El agente llama al tool MCP `harness_browser_start(job, version)` solo para explorar y `browser_close` al terminar; cada trabajo usa Chrome independiente. No esperes una reserva global antes de lanzar QA ni repitas suites para ocupar la espera. Antes de recheck/resultado exige que se haya cerrado la exploración. Si el QA se interrumpe, conserva su reporte parcial con qa-checkpoint y retoma desde ese checkpoint y los snapshots de tests; no vuelques conversaciones. Mantén un implementador y un QA por etapa: no añadas revisores paralelos por defecto ni actives /goal o /loop.

Al cerrar, muestra `specCompletion` del brief/show: las specs no ignoradas (versionadas o nuevas sin commit) viajan de Ready a specs/Done en el mismo PR, con sus recursos si usan carpeta propia; tras el merge se retira su copia local de Ready sin versionar y sin cambios (`local: removed_after_merge`) y `git pull` trae la de Done. Si `local` es `tracked_pull_required`, el pull la mueve. Las locales ignoradas se mueven tras completar el cierre sin sobrescribir cambios del usuario. El archivo con Estado: TERMINADO y sus recursos se conservan además en artifacts/completed-specs. Si se preservó el origen por cambios, recursos pendientes o colisión, informa las rutas; no borres ni sobrescribas para forzar el movimiento.

Diagnóstico y contexto: consulta `show`/brief una vez y lee solo el tramo del log que explica el fallo. No vuelques conversaciones anteriores, grafos completos ni todos los docs para recuperar una etapa. Si el bloqueo señala controlador/configuración, detente y registra la causa: no los edites durante un trabajo, no alteres hashes y no repitas verify/QA para intentar reparar una huella de publicación. Una actualización del paquete requiere cerrar los trabajos activos. Para documentación, entrega el diff aprobado y las secciones afectadas; no pidas reauditar todo el producto. Las métricas con transcript se acotan al trabajo y traspasos registrados; las ejecuciones antiguas sin inicio de prompt se marcan parciales. No traduzcas tokens de caché ni tiempo de estado en factura, cuota o cómputo activo.
