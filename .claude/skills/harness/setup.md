# Configuración asistida del harness

Objetivo: que el usuario no tenga que rellenar JSON ni averiguar comandos. Tú descubres, configuras y validas; pregunta solo decisiones que no puedas resolver con evidencia. Esta autorización permite editar `harness/config.json` y ajustes mínimos necesarios para emitir informes de pruebas; no permite extraer datos de producción ni aprobar funcionalidades.

1. Confirma la raíz Git/controlador y que no exista `.harness-parent.json`. Ejecuta `python3 harness/harness.py setup`: es una inspección, no ejecuta scripts. Si hay trabajos abiertos, conserva la configuración: no cambies hashes manualmente. Para el fallo específico de Flyway Docker host con conexión rechazada, el operador dispone de `repair-flyway-network <id>` con comprobaciones y preflight; el agente no lo ejecuta por su cuenta. No sobrescribas un setup funcional para volver a una plantilla. Si está configurado, verifica sus supuestos antes de cambiar algo.
2. Consulta Graphify para arquitectura y relaciones. Si falta o está desactualizado, `graphify . --code-only` y espera. Lee los manifests, lockfiles, scripts, configuración de tests/migraciones y documentación pertinente que indique la inspección. No leas `.env`, claves ni credenciales del origen. Elige el gestor indicado por el lockfile. Sigue las instrucciones del repositorio; no uses codebase-memory-mcp.
3. Identifica por separado el runner de Playwright CLI/tests para E2E repetibles y el MCP para exploración en Chrome visible. Reutiliza Playwright Java/JUnit si ya existe; en JS/TS usa Playwright Test. Configura las E2E repetibles en headless (sin ventana): revisa comando, scripts, configuración por proyecto, fixtures y variables de debug; evita `--headed`, `--ui`, `--debug` y `PWDEBUG` activo. En Playwright Test headless es el valor predeterminado; no añadas un flag `--headless` inexistente. Conserva el motor/canal de navegador requerido y el MCP exploratorio en Chrome visible. Configura comando, baseURL local e informes; si requiere el preview, QA lo ejecutará después del arranque, no en checks previos. No presentes el MCP como sustituto de tests persistentes. Deduce con evidencia servicios, carpetas, comandos de instalación/build/tests, rutas de informes JUnit, health checks, artefactos y variables para la conexión local. No inventes scripts `test:ci` ni declares `database.provider: none` porque falte una dependencia en un package.json: inspecciona backend y configuración; pregunta si persiste la duda. PostgreSQL y proyectos realmente sin base están soportados. Para otro motor informa la adaptación pendiente; no simules compatibilidad. Si backend y frontend tienen Git separados, conserva un único controlador en el backend. Declara `primaryRepository` y `repositories` con rutas a las raíces Git, y `repo` en pasos/servicios/reportes correspondientes. No instales un segundo harness en el frontend. Inspecciona y consulta Graphify en ambos; el setup registra sus manifests. Nunca resuelvas esto con `cwd: ../frontend`: cada ruta relativa queda dentro de su repo.
4. En proyectos nuevos usa `adapters/commands.py` y completa config.json según el contrato de [la guía](../../../docs/harness-claude-spec.md) (ruta desde la raíz: `docs/harness-claude-spec.md`). Conserva `adapters/sistema_juridico.py` únicamente en instalaciones que ya lo usen y correspondan a ese stack específico. Consulta las plantillas solo como ejemplos. Prefiere opciones CLI de reporteros ya instalados; añade una configuración mínima de reportero si hace falta, sin cambiar expectativas ni fabricar JUnit. Marca bloqueado si no hay pruebas; no sustituyas pruebas por un comando que siempre devuelve éxito. Si creas configuración adicional fuera de harness, debe llegar al worktree desde una base versionada. Para auxiliares de setup sin commit puede declararse `repositories.<nombre>.copyPaths` con rutas estrechas explícitas; excluye archivos ignorados y rechaza secretos. No copies cambios de producto ajenos. No hagas commits por tu cuenta.
5. Antes de ejecutar comandos, inspecciona los scripts y sus conexiones. Los procesos de aplicación deben escuchar en 127.0.0.1, usar los puertos `${PORT_<SERVICIO>}` y mantenerse en primer plano. Configura frontend/backend en orden de dependencia y `previewService`. Si el migrador corre dentro de Docker, no confundas loopback del contenedor con el del host. Para Flyway usa `--network container:${DB_CONTAINER}` y `jdbc:postgresql://127.0.0.1:5432/${DB_NAME}`; comprueba esa ruta con el preflight real. Declara `artifacts` para los builds y `integrationChecks` después de migrar si los tests requieren el clon preparado. Asegura que el entorno use variables del clon y que ninguna tarea cargue credenciales, envíe mensajes o conecte con servicios reales. No uses scripts de desarrollo compartidos para probar setup.
6. Si usa PostgreSQL y aún falta snapshot autorizado, pregunta por su ruta local y cuenta sintética. Puedes listar nombres/fechas de backups en ubicaciones indicadas por el usuario; no elijas un archivo solo por ser reciente, no abras datos ni extraigas de la principal. Una autorización anterior puede reutilizarse mientras el archivo y la configuración de base sean los mismos. Solo tras confirmar autorización/anonimización ejecuta:

   `python3 harness/harness.py setup --validate --snapshot /ruta/backup.dump --safe-snapshot --test-account cuenta-sintetica`

   Guarda únicamente ruta, hash e identificador de cuenta en `.harness/setup.json`, fuera de Git; no contraseñas. Si no hay backup, puedes terminar la configuración con estado `needs_snapshot`. No sustituyas la copia por una base vacía.
7. Cuando el JSON esté completo, pon `needsConfiguration: false` y ejecuta `python3 harness/harness.py setup --validate` (o el comando con snapshot anterior). Corrige errores deducibles y repite. Esta validación comprueba esquema y herramientas; con PostgreSQL también restaura el backup autorizado en un clon desechable y ejecuta `migrationSetup` y el comando real de `migrate` sobre copias temporales de los repositorios. Solo guarda `databasePreflight: passed` si funciona y limpia su clon. Si falla, setup queda `blocked`, no listo. `runtimeValidation: pending` sigue indicando que faltan las pruebas completas, el preview y QA. Configura `migrationSetup` si el migrador necesita dependencias o un build; no presupongas que estarán instalados en un checkout nuevo. Si faltan herramientas que requieren instalación o autenticación, presenta únicamente ese impedimento; no cambies a API de pago. No alteres una instalación global automáticamente.
8. Entrega un resultado breve: stack/servicios detectados, archivos ajustados, estado, cualquier pendiente y la siguiente orden `/harness specs/mi-feature.md`. La primera spec hará la verificación real en worktree y clon aislados; solo tras `verify` exitoso registra validación de ejecución. No afirmes que restauración, build, tests o Chrome pasaron durante setup si solo corriste doctor. No generes documentos por ejecución.

Para el uso diario el usuario no debe recordar ID, rama, puertos ni ruta del backup: `start` los resuelve o reutiliza. Antes del primer inicio de una spec, comprueba `spec-status`: la redacción empieza en borrador y `/harness ready <ruta>` solicita la autorización de esa versión. Setup no autoriza specs y la confirmación de readiness no inicia trabajos. Si los manifests de cualquiera de los repositorios cambian o el backup se sustituye, el controlador pide setup otra vez. Una respuesta de configuración nunca es una aprobación final de producto.

## Grupos de verificación y reutilización

Configura los grupos como parte del setup; el usuario no debe editar metadatos. En el adaptador `commands.py`, asigna IDs estables a cada paso de `setup`, `checks` y `build`; divide suites backend, unitarios frontend, tipos E2E y build frontend si los comandos del proyecto lo permiten. Conserva cada comando y su cobertura. Cada informe de `testReports` pertenece a exactamente un check mediante `reports: [nombre]`. Declara `cache: true` únicamente para pasos reproducibles. Las pruebas contra el clon/preview mantienen `usesDatabase: true` y nunca se reutilizan. Maven con Testcontainers independiente puede declarar `usesDatabase: false` si lo verificaste.

Cada grupo tiene `inputs: [{repo: nombre, exclude: [patrones]}]`, `dependsOn: [ids anteriores]`, `tools: [herramientas que influyen]` y `outputs: [artefactos relativos al repo]` cuando produce artefactos. Sin entradas explícitas se considera todo el repo. No uses exclusiones amplias sin inspeccionar scripts, imports y configuración. Excluye E2E de Maven/build/unitarios solo cuando no intervenga en ellos. Incluye contratos compartidos y migraciones en los grupos que realmente los consumen, mediante scopes de otros repositorios o dependencias. Un cambio fuera del alcance conocido invalida conservadoramente.

La instalación se ejecuta durante preparación y se reutiliza si las entradas, herramientas y `node_modules` siguen coherentes. Antes de excluir `src`, tests o E2E del grupo de instalación, comprueba scripts lifecycle y workspaces: conserva package.json, lockfiles, configuración del gestor, parches y archivos usados por postinstall/prepare. Declara el directorio instalado en `outputs`; usa `outputExcludes` solo para cachés generadas verificadas (por ejemplo `node_modules/.vite/**`, `.vite-temp/**` y `.cache/**` bajo node_modules), nunca para paquetes o ejecutables. Así los tests y el servidor no invalidan la instalación al escribir cachés. Nunca compartas node_modules por symlink. Si no puedes determinar entradas seguras, conserva el scope completo (más lento, verificable). `dependsOn` debe incluir la instalación correspondiente. Configura `inputs` en servicios para no reiniciar un preview por tests E2E que no importa.

Inspecciona helpers E2E y sus destinos antes de validar. No dejes problemas conocidos en `pendientes.e2e` para que QA los arregle durante una funcionalidad. El preflight estático bloquea esos pendientes, scripts/runners/informes ausentes y destinos fijos frecuentes en helpers. No prueba todos los caminos de conexión: debes revisar también imports, fallbacks y scripts invocados. Usa variables del trabajo y falla si faltan, sin fallback a una base compartida. Si corregirlos requiere cambios de producto fuera de setup, entrega el impedimento antes de iniciar specs. La emisión real de JUnit y los E2E siguen pendientes hasta ejecutar pruebas; nunca la declares validada con una inspección estática.


## Publicación y cierre

Configura `publication.enabled: true` para el flujo de PR y limpieza acordado. Descubre por cada raíz Git el remoto GitHub, su rama de destino y los workflows que se ejecutan para PR; pregunta solo si hay destinos ambiguos. Configura `publication.repositories` con las mismas claves que `repositories` (o `main` para un solo repositorio), `remote`, `base`, `workflows` y `requiredChecks` adicionales. Usa `pollSeconds: 30` y `timeoutSeconds: 3600`. GitHub CLI debe estar instalado y autenticado; `setup --validate` comprueba permisos de push, identidad Git, destino, reglas de checks y workflows activos mediante consultas de lectura. No crea PR ni modifica reglas. Si falta acceso o CI, queda bloqueado; no simules un pase ni desactives publicación para ocultarlo. No cambies el flujo de instalaciones anteriores sin aprobación.

Declara `disposablePaths` estrechos por repo únicamente para salidas generadas verificadas: por ejemplo `node_modules`, `target`, `dist`, `test-results`, `playwright-report`, `graphify-out`, y `harness/__pycache__` en el controlador. Revisa también outputs y cachés del stack. Nunca declares `src`, `docs`, `specs`, `e2e`, `.`, ni carpetas con trabajo manual. Los archivos ignorados desconocidos bloquean limpieza. Los tests nuevos y auxiliares de `copyPaths` que necesita CI sí se publican. Archivos del harness, secretos y artefactos no entran al PR; las modificaciones propias de preparación en `.gitignore`/CLAUDE.md se separan por su inventario inicial. No desactives hooks de validación; el commit del controlador usa `GRAPHIFY_SKIP_HOOK=1` para evitar regenerar el grafo al cerrar.

La aprobación humana autoriza documentación, PR y limpieza tras CI. El controlador explica esto en `approve`; no hay otra aprobación repetida. Solo los trabajos preparados con esta configuración capturan la política de cierre. Una actualización no publica ni elimina retrospectivamente trabajos anteriores.

## Suites E2E opcionales

`e2e` y `apiE2E` admiten `enabled: false`; si existe una sección sin ese campo se considera habilitada por compatibilidad. El preflight valida únicamente las suites habilitadas, incluidos runner, directorio, archivos de pruebas y destinos de conexión. Una suite Playwright habilitada sin archivos no vacíos `*.spec.*` o `*.test.*` bloquea setup antes de migraciones; la ejecución posterior debe comprobar el número real de tests. `apiE2E` no es obligatoria: si el backend ya tiene unitarios/integración y no necesita otra suite, deshabilítala explícitamente y conserva su carpeta. No crear tests de relleno ni activar suites por la mera existencia de un directorio. En la configuración actual, `apiE2E.testDir` y `report` son relativos a la raíz de su repo; en `e2e` son relativos a `cwd`. La configuración del runner reside en `cwd` en ambos casos.

## Referencias QA, permisos y cierre

La inspección devuelve `qaReferences`: revisa esas rutas para reutilizar login/fixtures/limpieza. Si faltan referencias de negocio, ubícalas con Graphify y pasa rutas/secciones concretas al agente; no fabriques datos genéricos. Los helpers del producto se cambian mediante su worktree y PR, no desde setup.

`cleanupPolicy` incluye automáticamente la ruta exacta `<cwd>/node_modules` de pasos declarados `npm ci` que tengan esa misma ruta en `outputs`, incluso `e2e/node_modules`. No convierte otros outputs en desechables ni permite borrar cualquier node_modules. Las suites deshabilitadas siguen deshabilitadas; retira su instalación solo si verificas que ninguna suite/helper habilitado la consume.

`permissions` distingue el modo solicitado de la política efectiva, que depende de Claude. No ejecutes acciones destructivas para probar permisos. Si la política real deniega una operación, informa su motivo y pregunta la decisión necesaria; no desactives verificaciones. Un timeout admite solo un reintento equivalente si el sistema lo permite.

Cada trabajo nuevo registra un entorno permitido y lo reutiliza al verificar/aprobar desde otras terminales. No edites sus huellas. Finalize admite PR abiertos respaldados y fusionados verificados (merge/squash/rebase), incluso si se eliminó la rama remota después del merge; PR cerrados sin fusionar siguen bloqueando.

Modo de uso: una spec por conversación, sin --launch. El instalador registra el hook local UserPromptSubmit y el MCP de Chrome en harness-qa; no necesitas otro setup en el frontend. Después de instalar/actualizar abre una nueva sesión de Claude Code en este controlador para cargar skill, agentes y hook. No cambies la autenticación ni permisos globales de esa sesión.

## Evidencias que no se pisan

Los reportes de checks deben quedar fuera del outputDir que Playwright borra al arrancar. Para Vitest usa `--outputFile.junit=.harness/reports/harness-unit.xml` y el mismo destino, relativo al repo/cwd, en `testReports`. Añade solo `.harness/reports` (con prefijo cwd si corresponde) a disposablePaths del repo; no toda `.harness`. Mantén el JUnit E2E en una ruta propia y archívalo por revisión. El preflight detecta colisiones con test-results y outputDir literales/configurados; si el proyecto lo calcula dinámicamente, revisa su destino efectivo. No cambies contenedores, base, permisos ni suites para resolver una colisión de archivos.

Actualización de instalaciones anteriores: si el controlador pide preflight de formato 2 y no hay trabajos abiertos, ejecuta `python3 harness/harness.py setup --refresh-tests`. Solo renueva la validación estática; no restaura el clon ni repite suites. Si cambiaron configuración/manifests o infraestructura ya registrada en formato 2, sigue la validación completa. Añadir o modificar tests/helpers seguros no exige repetir setup ni bloquea otra spec por sí solo.

Comprueba selectores Maven: los patrones globales `*Test`, `*Tests` y `*IT` necesitan también `*Test$*`, `*Tests$*` y `*IT$*` para incluir `@Nested`; extiende las exclusiones de clases externas a sus anidadas. `setup` bloquea selectores incompletos. `resources` es opcional: `heavySlots: 1`, `waitSeconds: 1800`, `minAvailableMiB: 512`; `resourceClass: heavy|light` permite clasificar un comando configurado. Estos límites solo coordinan comandos del controlador en esta instalación, no otros procesos/VMs.
